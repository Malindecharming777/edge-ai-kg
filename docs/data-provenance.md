# Data provenance

This KG mixes one real public source with a synthetic hardware fleet. The split
is deliberate and absolute -- read this before quoting any number from the graph.

## Real

**ONNX operator catalog** -- `data/onnx/operators.json`
Parsed from `docs/Operators.md` in [onnx/onnx](https://github.com/onnx/onnx),
Apache-2.0. 205 operators with their domain, latest opset version, and revision
count. Operator **names, domains and opset versions are real.** The `category`
field is ours (`etl/onnx_catalog.py`), a coarse grouping used to decide which
accelerator archetypes plausibly implement which operator.

## Synthetic

**Everything else.** Vendors, SoCs, accelerators, boards, runtimes, kernels,
models, variants, sensors, signal pipelines, clinical tasks, datasets and
deployments are generated by `etl/generate.py` from a seed.

Vendor, board and SoC names are **deliberately fictional** (`Corvid Silicon`,
`Nimbus Micro`, `Tessera Labs`, ...). No number in this graph is a claim about
any real product. That is a design constraint, not an oversight: attaching
invented latency or power figures to real part numbers would produce a dataset
that looks authoritative and is not.

Runtime names (TFLite Micro, ONNX Runtime, ExecuTorch, TVM microTVM, CMSIS-NN,
OpenVINO) and dataset names (MIT-BIH, PTB-XL, CHB-MIT, ...) are real projects
and real corpora, used as realistic labels. **The edges attaching them to
synthetic models and accelerators are invented.** No accuracy figure here was
measured on any of those datasets.

### Determinism

`--seed` (default `20260814`) fully determines the graph. Same seed and scale
produce the same nodes, edges and ids. `--scale` multiplies the fleet size;
`scale=1.0` yields ~23.8K nodes and ~72.9K edges.

### The cost model behind `Deployment` metrics

Deployment metrics are *derived*, not drawn at random, so they stay internally
consistent -- a board with no kernel for an operator really does pay for it:

1. A model's operators are split into those the target accelerator has a kernel
   for, and those it does not. The latter fraction is `fallback_fraction`.
2. Work is `2 x MACs`, split by that fraction between the accelerator and the
   SoC's CPU.
3. Each unit runs at `gops_int8 x precision_multiplier` (int8 is 3.2x fp32,
   int4 4.8x, fp16 1.7x).
4. `latency_ms` is the sum of both times, times a random 1.05-1.45 overhead
   factor for scheduling and memory traffic.
5. `energy_mj` weights each unit's time by its archetype's `energy_factor`
   (NPU-Pro 0.11, NPU-Lite 0.16, GPU 0.30, DSP 0.42, CPU 1.00).
6. `fits` is true when the working set fits both board RAM and flash.

**Limits of the model.** It ignores memory bandwidth, DMA setup, layer fusion,
cache behaviour, thermal throttling and per-operator kernel quality beyond a
single `efficiency` scalar. It is good enough to make the *structural* questions
("what falls back to CPU, and roughly what does that cost?") behave sensibly.
It is not a performance simulator, and the absolute numbers should never be
quoted as achievable.

### What the synthetic data is for

The interesting edge-AI deployment questions are structural: which operators
have no kernel on this accelerator; what breaks if a vendor drops a kernel;
which boards clear a latency budget for a regulated task. Answering those needs
**dense, complete coverage** of a hardware fleet crossed with a kernel library --
which no public dataset provides, and which cannot be honestly assembled from
real product names. So the fleet is synthetic and the questions are real.
